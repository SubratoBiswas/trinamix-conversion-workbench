the 03-Aug Customer documents, as dated entries that actually run

Two documents handed over on 03-Aug: "NXT Customer Field Mapping 1.xlsx"
(sheet "Source Files Mapping", 243 rows, 26 coloured Mapped) and
"customer_mapping.txt" (the transformation rules and the default values).
One instruction given on one day, so one file here and one date.

  app/data/customer_mapping_03aug.json — 54 statements, effective 2026-08-03:
  21 column mappings, 16 transformation rules, 16 constant defaults, one
  suppression, one duplicate source column. Generated by
  docs/build/make_customer_mapping_03aug.py so every entry is traceable to the
  sentence that produced it.

NO FAN-OUT, AND THAT IS THE POINT. The analyst asked for these to apply "to all
existing projects and future projects". Under the one dated store that is not a
job a seeder does — it is what the store is. Every entry is keyed (client,
source system, target field); every conversion, old or new, resolves against the
same rows at generate time.

WHAT WAS INERT
--------------
"Including the custom transformation rules" is the hard half, and three seams
each broke it on its own:

* apply_learned_to_conversion skipped any decision naming a column the extract
  does not have. Right for a column mapping; fatal for a rule, whose stored
  column is the literal "(rule)". EVERY multi-column rule in the store — every
  CONCAT, CASE_WHEN, COALESCE and SEQUENCE — hit that `continue` and did
  nothing. A rule now earns its way through on the columns its own config names.

* The write-time overlay read supplier files only. It now reads this one too, so
  the rules, constants and suppression are enforced where nothing downstream can
  undo them. It SKIPS rows scoped to particular sheets, because it is keyed by
  object and would put "Insert Update Indicator = I, profiles sheet only" on all
  nineteen.

* Both rule paths built the per-row context separately and only one carried the
  new pseudo-column, so an overlay rule reading it saw nothing on exactly the
  conversions this document is for.

WHAT THE DOCUMENT CHANGES
-------------------------
Seven of the nine July CW rules are rewritten:

  Party Type    now requires the organization name to be BLANK before it says
                PERSON. CW #22 tested first/last name alone, so every company
                carrying a contact's name came out PERSON.
  Party Number  is sequenced ON ENTITYID, not on the row index — a customer with
                five addresses was taking five different party numbers while the
                eighteen sheets that reference the party still held one. Both
                forms are six digits, which settles the open question CW #23 was
                left carrying.
  _B / _S and   now read WHICH SOURCE SHEET the row came from, as the analyst
  BILL_TO /     wrote it. CW #19/#24 read the Default Billing / Default Shipping
  SHIP_TO       flags, which mark the DEFAULT address rather than the sheet, so a
                customer's second billing address was neither. Suffixes are
                capitals now.
  Contact Point Type no longer defaults to a flat PHONE on rows that carry
                neither an email nor a number.
  Phone Line Type reads the plain Phone column for MOBILE, not "Mobile Phone".
  Party Site Name gains the "addresslabel" spelling.

CW #15 is restated unchanged so the whole instruction carries one date. CW #18
is not mentioned by the new document and is left exactly as it was.

ENGINE
------
* config["then"] chains rules inside ONE entry. The store holds one rule per
  field — that is what makes "newest wins" decidable — but "concatenate entityid
  and internalid, and add _B on a billing row" is one sentence needing two rule
  types. Split across two entries the store keeps one and the field ships half
  its key.
* CASE_WHEN branches take `all` / `any`. "Organization name blank AND a person
  name not blank" cannot be said as separate branches: the first to match wins
  and the organization test is never reached.
* Every rule column may be a LIST of candidate spellings, everywhere — CONCAT,
  COALESCE, CASE_WHEN, SUFFIX_WHEN and the SEQUENCE variant. One guessed
  spelling binds to nothing and fails silently in a file that looks correct.
* SEQUENCE takes key_column, indexed once over the whole frame before chunking.
  A key column the extract lacks falls back to the row index rather than
  blanking the column; a row whose key IS blank gets nothing rather than
  somebody else's number.

PRECEDENCE
----------
* Every entry is scoped to the 19 Customer interface sheets. Not a tier — it is
  what the document is about, and it is load-bearing: MEASURED against the
  shipped JSON, 14 of these 53 target fields are also claimed by the supplier,
  HCM or catalog documents. Unscoped, "Payment Terms = IMMEDIATE" — the newest
  statement in the store — would have become the answer for Supplier Site.
* The three keys CW_Issues 2 scoped on 29-Jul name their exclusions again rather
  than trusting the union, so restating them cannot widen them.
* An overlay RULE no longer runs over a conversion's own rule that is NEWER than
  the document. Whichever is latest, now answerable for rules and not only for
  constants and suppressions.
* "Apply the authored Customer rules" no longer hands out the seven superseded
  ones. It would have written the July version stamped with today, and a newer
  conversion rule wins — a button labelled "apply the analyst's rules" quietly
  undoing them. The list is derived from the later file, not hand-kept.

OPEN, AND IN THE FILE UNDER _open_questions
-------------------------------------------
* Phone Line Type opens "can have values as MOBILE or PHONE" and then assigns
  MOBILE or FAX. The two conditionals are implemented as written; PHONE is not
  reachable by either.
* Identifying Address: "T to be kept as Yes and others flagged as N". Yes and N
  are not the same vocabulary; implemented Y/N, which is what the flag takes.
* Party Number is generated for every party (preserve_source off).
* The sheet-based rules need the two address extracts uploaded as separate
  sources with "Billing" / "Shipping" in their names.

every duplicate group, not the hundred that fit on screen

The panel returns at most max_clusters groups. On the NextPower supplier run that
is 100 of 342, and the banner said so honestly — "242 more are not listed and
cannot be decided here … raise the limit to review them all" — beside no control
that raised it. A message asking somebody to do a thing the screen cannot do is
worse than no message: it reads as their oversight.

The API has accepted max_clusters up to 2000 since the truncation was first
reported. Only the client hardcoded 100.

TWO ANSWERS
-----------
1. "Load all N groups" on the banner itself, so the other 242 become decidable.
   Asks for cluster_count + 10, clamped to the endpoint's 2000, so an over-large
   request cannot come back as a 422 the analyst reads as a broken page.

2. GET /conversions/{id}/duplicate-suspects-export — every group as an .xlsx.
   342 groups over 831 records is not a list anyone reviews by scrolling, and the
   question actually being asked of it is a filter and a sort.

   Summary — found vs listed vs decided, kept as separate numbers because
     reporting one of them is how "0 undecided" came to sit beside "342
     suspected groups". Carries the scan-coverage note and says whether AI
     adjudicated.
   Groups — one row per record, grouped, with the identity values carried so the
     file stands alone, and the match stated once per group rather than repeated
     down nine rows as nine findings.
   Conflicting IDs — one row per strong identifier a group DISAGREES on, with
     the actual differing values.

WHY THAT THIRD SHEET
--------------------
The live case. Nine "Flextronics Technologies India" rows at 100% name match
carrying three Tax Registration Numbers, four D-U-N-S numbers and nine Supplier
Numbers. Merging keeps ONE value per column — survivor first, then first
non-blank — and discards the rest, so whether that group is one entity decides
whether merging is correct or destroys eight supplier numbers. Not answerable
while 242 sibling groups are invisible.

The conflict stays ADVISORY, here as in the panel. A differing tax id usually
means separate legal entities, but it can equally be one source recording the
number wrong, and splitting the group automatically would hide a real duplicate.
That judgement does not move into a spreadsheet because the spreadsheet is
easier to read. The values are named rather than flagged, so a person can see
three GSTINs sharing one PAN and decide; a boolean sends them back to the screen
they were trying to leave.

ONE SCAN, TWO READERS
---------------------
_scan_duplicates is extracted and called by both endpoints. The export exists to
show what the panel truncates, so an export that scanned differently would answer
a different question from the screen it completes — and a second copy of a rule
drifting from the first is the defect this codebase repeats most.

The export is deterministic only (use_ai=False). AI adjudication is a decision
aid on screen; silently baked into a file somebody will act on it becomes an
unattributed judgement.

the whole list, paged — and "all" means all

Clarified by the analyst: the panel should hold the ENTIRE list (342 groups on
the NextPower supplier run, a different number on every other conversion), paged
for reading, and "Merge all high-confidence (>=95%)" should apply to all of them.

The previous commit added a button that loaded them on request. That was the
wrong shape. Asking somebody to opt in to seeing their own data leaves the
default wrong, and the default was the actual defect: the client asked for 100
groups, so every counter and every bulk action covered the visible third while
the labels said "all". "Merge all high-confidence · 100" merged 100 of 342 and
called it all. Nothing on screen distinguished that from a completed review.

  * The scan is requested at the endpoint's ceiling. Cheap: the scanner computes
    every cluster and then SLICES, so the cap saved no work, only payload — 342
    groups over 831 records is a small response.
  * The panel pages the RENDER at 25 groups. That is what the old cap was really
    protecting against — mounting 342 group tables at once — and it protected
    against it by hiding the data and then reporting on what was left.
  * The list is not paged. highConfidenceTargets, the decided/undecided pills and
    both bulk actions read `dupes.clusters` — everything — so the button now says
    the true number and merges it in ONE saveDecisions call, page or no page.

The page indicator says so out loud ("every count and every bulk action above
covers all 342 — not this page"), because a paged list is exactly where a reader
starts assuming the button means the page. The merge confirmation says it too,
and now also says what a merge costs: one value per column survives, so where a
group disagrees on a supplier number, a tax registration or a D-U-N-S, every
other value is gone from the output.

The page number is clamped rather than trusted — clearing decisions or
re-scanning can shorten the list under a page number that was valid a moment ago,
and an out-of-range page renders as an empty panel that looks like a failed load.
A fresh scan returns to page 1.

The truncation banner stays for the case it is still true in: past 2,000 groups
the scan is genuinely truncated, and a truncated review list that reads as a
complete one is the failure this panel was corrected for.

Tests: 996 passing, 14 skipped (was 992). The paging tests assert the seam
specifically — the render reads the page, the merge target reads the list — since
that is the one way paging could put the original bug back.

a blank Converted Data panel that will not say why, and the source file you could not open

Reported live: "Syteline source -> Item Import", Converted Data 0, column headers
rendering perfectly, Lineage 260, Cleansing 18, nothing underneath. The question
was "why is there nothing for this?" and the screen had no answer anywhere on it.

FOUR DEFECTS, all in that one path.

1. ZERO ROWS WITH COLUMNS FELL THROUGH TO THE TABLE. renderData handled only
   `columns.length === 0`, so a frame with 260 columns and no rows drew a header
   row over an empty body. A blank panel cannot be told apart from a failed load,
   a page still working, or a conversion that genuinely produced nothing — and
   those need different responses. The cause is named now: nothing mapped, an
   empty source, every record excluded by a decision, or rows read and then lost.
   Each branch is DERIVED from the conversion, and the last one says what to check
   rather than inventing a cause that sounds plausible.

2. THE BADGE WAS NOT COUNTING WHAT IT SAID. total_rows returned the SOURCE
   dataset's row count wherever it could resolve one, under a label reading
   "Converted Data". The two agree on a healthy 1:1 conversion and diverge exactly
   when something has gone wrong, which is the only time anybody reads them. It is
   now the source total where the conversion produced rows and 0 where it produced
   none, with both numbers reported separately so the gap is visible.

3. IT READ conversion.dataset_id — the singular, legacy field — so a multi-source
   conversion never resolved it and fell back to the length of a 50-row preview.
   The badge would report 50 for a 12,000-row extract. It reads every bound
   dataset now.

4. THERE WAS NO WAY TO DOWNLOAD A SOURCE FILE. Everything downloadable was
   output-side — the FBDI bundle, the run report, the mapping export, the
   duplicate list — so the one artefact that settles a disagreement between the
   tool and the data was the one artefact nobody could open. On a dataset card
   reading "0 rows x 165 cols" against a conversion producing nothing, opening
   the workbook IS the investigation.

   GET /datasets/{id}/download, and a Download button beside Replace on the
   conversion's source card. Served through materialize_dataset_file, the same
   rehydration generation uses, so it cannot hand back a file the conversion is
   not reading — the disk is ephemeral and a dataset older than one deploy has no
   local copy. Missing bytes say "re-upload the file" instead of a bare 404. The
   original filename is preserved, which matters here: this case has three cards
   all called some variant of "Syteline source".

===============================================================
mapping and generation: a thousand round trips become two

Reported by the analysts working from India: the tool is slow on mapping and
output generation.

It is not the work. The transforms run on pandas in a worker thread and finish in
milliseconds. The cost is how many times one request goes to the database and
back, in sequence:

  * the mapping run saves one document per target field — well over a thousand on
    the 19-sheet Customer template
  * the apply-learnings pass at generate writes one per field again

At 2ms to the cluster that is a couple of seconds nobody notices. At 250ms — an
app and a cluster in different regions, or a long link to a cold free-tier
instance — it is FOUR MINUTES for byte-identical code.

Which is exactly why it read as intermittent and unfixable. Nothing in the code
distinguishes the fast case from the slow one, so the same click is instant on
one desk and a timeout on another, and a profiler on the fast machine shows
nothing wrong. Nobody suspects the code because the code looks fine.

services/bulk_write.py — BulkPatcher queues {document: patch} and sends one
bulk_write per collection; bulk_increment does the same for counters, which are
the worst offenders per unit of value (a field nobody reads during the run,
costing a full hop every time it moves).

  mapping_service.save_ai_mappings  ~1,400 hops -> 2 (one update batch, one
                                    insert_many)
  apply_learned_to_conversion       ~1,400 hops -> 2 (one patch batch, one
                                    counter batch)

WHAT IS DELIBERATELY UNCHANGED
------------------------------
* WHAT gets written, and WHEN the decision to write is made. The "only write what
  actually changed" rule in the apply pass is untouched and still load-bearing —
  it is what keeps the queue empty on a re-generate that resolves to what is
  already stored. Batching does not replace it; it removes the cost of the writes
  that do have to happen.
* Reading a field back after setting it. BulkPatcher.set applies the patch to the
  in-memory document immediately, on purpose: several callers do exactly that,
  and making them wait for the flush would turn a latency fix into a silent data
  bug.
* Failure handling. flush raises what the driver raises. A batch that quietly
  dropped half its updates would be far worse than a slow one — the screen would
  show the new value and the file would carry the old, which is the single most
  expensive shape of bug in this tool.

insert_many is only safe in the mapping run because the apply-learnings pass runs
on those same objects immediately afterwards; rows without ids would queue
updates against None and silently do nothing, which is a faster no-op. The ids
are read back and attached.

tests/test_round_trips.py counts HOPS rather than measuring time — a timing
assertion on a shared runner is a flake, and the hop count is what actually
changed. 1,035 passing, 14 skipped (was 1,020).

STILL OUTSIDE THE CODE, and likely larger than all of this: if the Render service
and the MongoDB Atlas cluster are not in the same region, every remaining hop
still pays that crossing. Worth checking both regions in the dashboards before
anything else — it is a settings change, not a deploy.

launch_git.bat carries the deploy set, so a partial deploy cannot start

Standing instruction, given twice: the deploy lives in launch_git.bat. It had
drifted -- the script knew how to apply whatever .patch files it found, and
knowing WHICH ones this deploy needs had moved into a covering note beside the
download. A note is a thing you have to have read.

EXPECT now names every patch this deploy needs, in apply order, and the script
checks the set before touching anything. A missing patch stops the run, names the
files and changes nothing -- half a deploy commits, pushes and builds green with
the change not in it, which is far harder to notice than a script that refused to
start. A leftover patch from an earlier deploy is reported rather than treated as
an error, because an unexpected file is also what a MISNAMED new patch looks
like.


===============================================================

launch_git.bat: carry the deploy set, and never claim a deploy that did not happen

Two changes, one of them a defect in this script that it existed to prevent.

1. IT REPORTED SUCCESS ON A RUN THAT DEPLOYED NOTHING.

   Observed: one already-applied patch skipped, "nothing to commit, working tree
   clean", "Everything up-to-date", and then "DONE - committed and pushed" with a
   SHA that was simply whatever was already on main.

   The verify asked "is anything STILL STAGED?" and treated a clean index as
   proof of a commit. But a run with no patches in the folder also leaves a clean
   index -- there was nothing to stage in the first place -- so "committed
   nothing because there was nothing to commit" and "committed successfully"
   printed identically, and the script went on to push and congratulate itself.

   HEAD is now captured before the commit and compared after. A HEAD that did not
   move stops the run, lists every patch this deploy needs, and says outright
   that nothing was pushed. On success it prints the transition
   (from 5fac909 to a1b2c3d) rather than a SHA that proves nothing.

2. IT CARRIES THE DEPLOY SET. Standing instruction from the analyst, given
   twice: the deploy lives in this file. EXPECT names every patch this deploy
   needs, in apply order, checked BEFORE anything is touched. A patch still
   sitting in the downloads folder stops the run and is named. A leftover from an
   earlier deploy is reported rather than treated as an error -- it is skipped as
   already-applied anyway, and an unexpected filename is also what a MISNAMED new
   patch looks like.

Plus: patches now apply in forced name order (`dir /b /o:n`, not the bare glob,
whose order the filesystem chooses), because later patches are cut on top of
earlier ones -- and the revert hint names only the patches THIS run applied,
where before it listed every .patch in the folder including ones it had skipped
as already live. Following that hint would have reverted a deployed change.

3. IT NOW RUNS FROM A COPY IN %TEMP%, and that is required rather than tidy.

   This script is delivered as a patch now, so a deploy PATCHES THIS FILE while
   it is running. cmd.exe does not load a batch file into memory -- it reads one
   command, seeks back to a stored BYTE OFFSET, and reads the next. Rewrite the
   file underneath that and the next seek lands mid-line, and the remainder of
   the deploy executes as garbage.

   It copies itself to %TEMP%, re-runs from there and passes the real repo
   directory through, because %~dp0 inside the copy points at %TEMP%.
